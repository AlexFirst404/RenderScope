# Методика и границы измерений

RenderScope связывает вызовы мировых EntityRenderer и BlockEntityRenderer с их registry ID, модом и экземпляром. Результат помогает найти объект для проверки в сцене; он не является полным системным профилем Minecraft.

## Время вызова

Основной таймер — `System.nanoTime()` непосредственно вокруг конкретного `renderer.render(...)`. Единица интерфейса — миллисекунда.

**Measured CPU-side render time** означает прошедшее время вызова на клиентском потоке. В него могут входить Java-вычисления, подготовка геометрии, отправка команд, ожидание драйвера и другие блокировки внутри вызова. Это не измерение времени исполнения GPU. RenderScope 0.1.0 не использует OpenGL timer queries и не показывает per-object GPU timing или VRAM.

В Settings можно отдельно включить `ThreadMXBean` current-thread CPU timing. Он собирается только при поддержке и доступности соответствующего JVM-счётчика; основной wall-clock таймер от него не зависит. Это дополнительная CPU-метрика, а не замена измерению прошедшего времени.

Scope завершается в `finally`; если исходный renderer выбрасывает исключение, время и failure учитываются, а исключение продолжает обычный путь обработки. Вложенные измеренные renderer calls учитываются **exclusive**: из времени родителя вычитается полный сырой интервал дочернего вызова, включая его собственных потомков. То же правило применяется к доступному thread CPU time. Таким образом, инструментированные вложенные вызовы не прибавляют один и тот же интервал к нескольким строкам. Количество invocations и failures при этом остаётся фактическим для каждого вызова.

## Что входит в проценты

Mods группируется по namespace registry ID: `minecraft:chest` относится к Minecraft независимо от того, какой мод влияет на реализацию рендера. Отдельно показываются имя Java-класса рендерера и найденный владелец его пакета.

`% Render` — доля в сумме **измеренных renderer calls**, а не доля всего времени GPU или всех подсистем клиента. Отрисовка terrain, частицы, GUI, самостоятельные item-renderer вызовы и отдельные shader passes не атрибутируются этим MVP. Нагрузка вне instrumented dispatcher path может отсутствовать в таблицах. Mixin-вмешательства в чужой класс не могут быть точно разделены по авторам инъекций.

## Rolling window и статистика

Стандартное окно — последние **5 секунд**; в настройках доступны 1–30 секунд. Для каждого mod/type/renderer/instance сначала суммируются его вызовы внутри каждого кадра.

| Поле | Значение |
| --- | --- |
| Average / Render ms | Сумма измеренного времени объекта, делённая на количество кадров окна |
| P95 | 95-й процентиль покадровой суммы времени соответствующей строки |
| Peak | Максимальная покадровая сумма времени строки |
| Calls/f | Количество renderer invocations, делённое на количество кадров |
| Calls in window | Фактическое число вызовов за окно |
| Instances | Количество различных измеренных ключей экземпляров за окно |
| Vertices / estimated bytes | Наблюдаемая геометрия в среднем на кадр, когда включён Full |

Кадры, в которых конкретный объект не рендерился, входят в знаменатель и в распределение как нули. Поэтому строка редко видимого объекта не выдаёт среднее одного дорогого вызова за постоянную нагрузку каждого кадра. P95 и peak в UI относятся к кадрам, а не к отдельным invocation samples.

Rolling-процентили вычисляются по сохранённым значениям точно. Память имеет жёсткие лимиты; в очень насыщенной сцене удерживаемая история может стать короче выбранного временного окна. `droppedMeasurements` в JSON позволяет обнаружить потерю детализации.

## Время кадра и FPS

Границы кадра находятся у входа и возврата `Minecraft.runTick`. Это длительность клиентского кадра, включающая работу интерфейса, мира и возможные ожидания внутри данной границы. Она не равна сумме времени измеренных entity/block entity calls.

Средний FPS равен `1000 / averageFrameMs`. `1% low FPS` вычисляется как `1000 / mean(slowest 1% frame times)`; это не просто обратная величина P99. P50/P95/P99 и worst frame описывают время кадров в соответствующем окне или capture.

Сам профилировщик и включённые оверлеи выполняют работу на клиенте. Для сравнения сцен используйте одинаковые настройки, разрешение, GUI scale, дистанцию, FPS cap и режим измерения. Не интерпретируйте единичное значение из случайного кадра как универсальную характеристику мода.

## Геометрия: Full mode

RenderScope не оборачивает чужие `VertexConsumer`. Вместо этого он наблюдает стандартные точки:

- завершение `BufferBuilder.endVertex` во время активного renderer scope;
- текущий размер vertex format для оценки байтов;
- запросы `MultiBufferSource.BufferSource.getBuffer(RenderType)`.

Для наблюдаемой геометрии `estimated bytes = Σ vertex format size` по завершённым вершинам. Это **Estimated vertex data**. Батчинг, переиспользование, последующие преобразования и фактические GPU uploads могут отличаться.

Альтернативные consumer/buffer implementations, собственные GPU pipelines и некоторые оптимизирующие моды могут обходить эти методы. Поэтому нулевой счётчик в Full не доказывает отсутствие геометрии, а найденные RenderType — список наблюдаемых запросов, не полный GPU command trace. Имена RenderType ограничены по длине и количеству для ограничения памяти.

В Timing Only геометрия не собирается и в интерфейсе показывается прочерк. При сравнении отчётов учитывайте сохранённый `measurementMode`. Во время одной записи лучше сохранять один режим измерения: переключение меняет полноту геометрии внутри этой записи.

## Timeline и spikes

Живая история охватывает примерно 30 секунд и хранит до десяти репрезентативных кадров в секунду. В каждом интервале сохраняется настоящий кадр: spike имеет приоритет, иначе выбирается самый медленный. График не содержит синтетических средних кадров.

Spike отмечается, если время кадра превышает одновременно примерно **33,33 мс** и **1,75×** сглаженную предыдущую базу. Marker сообщает о временном выбросе относительно текущей работы, а не о доказанной причине.

При выборе точки показываются измеренные времена соответствующего кадра, до пяти верхних registry-owner модов и самый дорогой измеренный экземпляр этого кадра. Это историческая атрибуция, даже если объект уже вышел из видимости.

## Heatmap и экземпляры

Теплокарта ранжирует подходящие измеренные экземпляры по rolling average. Цвет определяется относительным рангом; верхние 5% оказываются в красной зоне. Расстояние, категории и minimum cost сначала ограничивают набор кандидатов. Дополнительно применяется max highlighted objects. Подписи ограничены 32 и пропускаются при экранных пересечениях или наложении на HUD; выбранные и дорогие объекты имеют приоритет. Поэтому при Show labels = ON количество подписей может быть меньше числа bounding boxes.

При уходе объекта из видимости его данные постепенно выпадают из rolling window. Подсветка и tracking хранят ключи и value records; entity для актуального bounding box ищется по ID в текущем мире. Смена мира или dimension сбрасывает сессию и выделения. Tracking не телепортирует игрока и не меняет сам объект.

## Capture и экспорт

Capture агрегирует каждый завершённый кадр записи, независимо от длины rolling window. Длительности: 5/10/30 секунд или ручная остановка. Capture-процентили и 1% low используют ограниченную логарифмическую гистограмму с отношением соседних buckets **1,022** (около 2,2%); это приблизительная статистика. Среднее, суммы вызовов и peak не получают эту гистограммную аппроксимацию.

При длительной ручной записи capture timeline сокращается с сохранением худших кадров в объединяемых интервалах. Лимиты числа ключей и `droppedMeasurements` должны учитываться при анализе крайне больших сцен.

JSON содержит разрешённые версионные, модовые и измерительные поля. По умолчанию он не содержит dimension/coordinates, UUID, player name, server address/hostname, world name, chat или absolute paths. Включение **Include world positions** добавляет только position и dimension к соответствующим экземплярам. Список установленных модов и их версии включается всегда. Файл остаётся локальным, пока пользователь сам не решит им поделиться.
